# TrueQuery floor — non-negotiables

The skill teaches everything below; the checker proves
violations. Never claim more than the registry says: only
the checked section runs in `truequery` today.

## Checked by `truequery` (enabled rules)

- `model/unique-key-merge-key` [error] Every model using a merge or delete-plus-insert incremental strategy must declare its merge key (unique_key) and every key column must be NOT NULL with one row per key value in each processed batch.
- `sql/accidental-cross-join` [error] No query block joins two table expressions without an explicit linking predicate (ON/USING) unless the join is written as an explicit CROSS JOIN; comma-separated FROM lists contain at most one table expression. This record owns the comma-join ban for the whole pack.
- `sql/between-date-on-timestamp` [warning] A filter on a TIMESTAMP (or DATETIME) column uses a half-open range, ts >= start AND ts < end_exclusive, never BETWEEN with date-only bounds such as BETWEEN '2024-01-01' AND '2024-01-31'.
- `sql/case-without-else-in-aggregate` [advisory] A CASE expression whose result feeds an aggregate (SUM, AVG), arithmetic, or a filter has an explicit ELSE branch (ELSE 0, ELSE NULL, or ELSE an explicit bucket such as 'unknown'), so the value for unmatched rows is a visible decision.
- `sql/count-star-after-left-join` [error] When a query LEFT JOINs a parent to a child table and counts children per parent, it counts a non-null child column (COUNT(child.key)), never COUNT(*) or COUNT(1).
- `sql/group-by-bare-column` [warning] On engines that silently accept ungrouped columns in an aggregate query (MySQL with ONLY_FULL_GROUP_BY disabled, SQLite), every projected column under GROUP BY is a grouping key, wrapped in an aggregate, or wrapped in an explicit arbitrariness marker such as ANY_VALUE(). Engines that reject the query (DuckDB, Postgres, BigQuery, Snowflake, MySQL in its default mode) need no lint: the error already stops it.
- `sql/insert-explicit-column-list` [warning] Every INSERT INTO names the target columns explicitly and projects the source in the same order (or uses a by-name form such as DuckDB's INSERT INTO ... BY NAME); positional INSERT without a column list is rejected.
- `sql/integer-division-truncation` [warning] In dialects where integer / integer yields an integer (Postgres, SQL Server, SQLite), a division whose operands are both integer-typed casts one operand to NUMERIC/DECIMAL/DOUBLE (or multiplies by 1.0) before dividing. In DuckDB, the integer-division operator // (and divide()) is used only when truncation is intended.
- `sql/left-join-null-rejecting-where` [warning] Predicates on columns of the nullable side of a LEFT, RIGHT, or FULL join appear in the ON clause; the WHERE clause never null-rejects those columns unless the inner-join conversion is intended and recorded.
- `sql/natural-join-explicit-keys` [warning] Joins name their keys with an explicit ON or USING list; NATURAL JOIN is rejected. (Comma joins without a predicate are covered by sql/accidental-cross-join, not by this record.)
- `sql/nondeterministic-merge-keys` [error] Merge keys, dedupe keys, and incremental watermarks never call per-row nondeterministic functions (RAND, RANDOM, UUID, GEN_RANDOM_UUID, NEWID); wall-clock calls in keys are replaced by deterministic business keys, and templates are checked pre-render so Jinja markers like is_incremental do not hide the call.
- `sql/not-in-nullable-subquery` [error] Any NOT IN whose subquery column is nullable is rewritten as NOT EXISTS (correlated) or the subquery explicitly excludes NULLs.
- `sql/null-equality-comparison` [error] A comparison against the NULL literal is written IS NULL / IS NOT NULL (or IS [NOT] DISTINCT FROM for a nullable value); the forms = NULL, <> NULL and != NULL never appear in a predicate.
- `sql/row-number-dedupe-tiebreaker` [warning] Every ROW_NUMBER used to pick one row per group (QUALIFY rn = 1 or equivalent) has an ORDER BY whose columns are unique within the partition.
- `sql/unguarded-update-delete` [error] Every UPDATE or DELETE has a WHERE clause (or WHERE CURRENT OF), or carries an explicit full-table marker such as a deliberate TRUNCATE or a reviewed full_refresh flag; unguarded whole-table mutations are rejected.

## Taught, not checked yet (disabled rules)

- `dq/uniqueness-key-no-duplicates` [error] Every declared primary key or unique identifier has a check asserting zero duplicate values (COUNT(*) minus COUNT(DISTINCT key) equals zero), enforced on every write to the table. (off by default: not yet precise enough to run unasked)
- `ingest/declare-source-freshness` [warning] Every source consumed by a pipeline MUST declare the timestamp column that defines its freshness (a loaded-at or event-time field) and a maximum acceptable data age with a warn and an error limit, and the pipeline MUST evaluate that threshold on each run, reporting the run time, the newest data timestamp and the resulting lag. Static reference tables that never change are marked frozen instead. Sources that feed critical outputs additionally declare a criticality tier, an owner and an alert route, so a breach pages a person rather than landing in an unmonitored channel; non-critical sources need the thresholds only. (off by default: not yet precise enough to run unasked)
- `orch/explicit-catchup-policy` [warning] Every scheduled Airflow DAG MUST pass `catchup` explicitly (False, or True with a bounded start_date and rerun-safe logic) instead of inheriting `[scheduler] catchup_by_default`. The inherited value is version- and config-dependent: it defaulted to True in Airflow 2.x and defaults to False from Airflow 3.0, and any deployment can override it. (off by default: not yet precise enough to run unasked)
- `sql/average-of-ratios` [warning] When a query reports a ratio (rate, share, conversion, margin) over more than one row, it divides the summed numerator by the summed denominator. It does not AVG a column or expression that is already a per-row ratio, unless the unweighted mean of row ratios is explicitly what is wanted and is labelled as such. (off by default: not yet precise enough to run unasked)
- `sql/distinct-dedup-bandaid` [warning] SELECT DISTINCT over a join is rejected unless the author records the business key it dedupes by and why duplicates are legitimate; the default fix is correcting the join grain, pre-aggregating, or using EXISTS. (off by default: not yet precise enough to run unasked)
- `sql/keyset-pagination` [warning] Queries that page through a table that can change between page fetches use a keyset predicate on a unique ordered key (WHERE key > :last_seen ORDER BY key LIMIT n) instead of LIMIT plus OFFSET, and page ordering always includes a unique tiebreaker. Large literal OFFSETs (default threshold 10,000) are flagged for cost as well. (off by default: not yet precise enough to run unasked)
- `sql/limit-requires-order-by` [warning] Any query block with LIMIT or FETCH FIRST also has an ORDER BY, unless the limit is a bare existence probe (LIMIT 1 whose projected values are not used). The ORDER BY must also be over a key that is unique in the result. These are two separate checks: the detector flags only a MISSING ORDER BY; proving that the ORDER BY keys are unique needs declared uniqueness facts and is left to contract mode. (off by default: not yet precise enough to run unasked)
- `sql/negative-filter-drops-nulls` [warning] A negative predicate on a nullable column (col <> 'x', col != 'x', col NOT LIKE 'p%', col NOT IN ('a', 'b')) makes an explicit NULL decision in the same query: IS DISTINCT FROM 'x', OR col IS NULL, AND col IS NOT NULL, or a COALESCE. This is a heuristic: excluding NULLs may be intended, and the rule only asks that the choice be visible. (off by default: not yet precise enough to run unasked)
- `sql/set-operation-column-position` [error] Every branch of a UNION, INTERSECT, or EXCEPT projects the same columns in the same order with compatible types, verified by alias and type comparison across branches; branches never use SELECT * and branches with mismatched names fail review. (off by default: not yet precise enough to run unasked)
- `sql/union-all-default` [warning] UNION and UNION ALL answer different questions, and which one is right depends on intent. UNION (DISTINCT) is correct when the author wants the set of distinct rows across branches; UNION ALL is correct when appending rows that can legitimately repeat (events, transactions, log lines). A bare UNION is flagged until the author records that dedup is intended; appends use UNION ALL. (off by default: not yet precise enough to run unasked)
